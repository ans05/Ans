# Database schema (PostgreSQL 16)

Managed by Alembic. Conventions: `bigint` identity PKs for high-volume tables, `uuid` where the client generates IDs, `timestamptz` everywhere (UTC), `CHECK` constraints/enums for closed sets.

```
users 1──* listening_sessions 1──* streams 1──* stream_events
artists 1──* tracks 1──* streams
                      request_metrics    (API, app-level)
                      cdn_requests       (CloudFront logs, AWS)
                      flow_log_records   (VPC Flow Logs, AWS)
                      anomalies          (detector output)
```

## Core content

```sql
users(
  id bigint PK, username text UNIQUE NOT NULL, is_simulated bool NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now())

artists(id bigint PK, name text UNIQUE NOT NULL, bio text, created_at timestamptz)

tracks(
  id bigint PK, artist_id bigint FK→artists NOT NULL, title text NOT NULL,
  duration_seconds int NOT NULL CHECK (duration_seconds > 0),
  audio_key text NOT NULL, artwork_key text, genre text,
  license text NOT NULL,            -- e.g. 'original-synthesised', 'CC0'
  created_at timestamptz NOT NULL DEFAULT now())
-- API returns audio_url/artwork_url built from MEDIA_BASE_URL + key
```

## Listener telemetry (application-level)

```sql
listening_sessions(
  id uuid PK,                       -- generated by browser
  user_id bigint FK→users NOT NULL,
  started_at timestamptz NOT NULL, ended_at timestamptz,
  data_source text NOT NULL CHECK (data_source IN ('real','simulated')),
  user_agent text, connection_type text,     -- navigator.connection.effectiveType if available
  avg_client_rtt_ms real)                    -- rolled up; convenient for "network quality vs session duration"

streams(                            -- ONE ROW PER PLAY ATTEMPT (derived at ingest)
  id uuid PK,                       -- stream_id, generated by browser per track load
  session_id uuid FK NOT NULL, track_id bigint FK NOT NULL,
  started_at timestamptz NOT NULL,
  outcome text NOT NULL DEFAULT 'in_progress'
      CHECK (outcome IN ('in_progress','completed','skipped','abandoned')),
  listened_seconds real NOT NULL DEFAULT 0,
  time_to_first_audio_ms int,       -- real: click → 'playing'
  load_time_ms int,                 -- real: Resource Timing responseEnd - startTime for audio
  ttfb_ms int,                      -- real: Resource Timing
  client_rtt_ms int,                -- real: timed /api/ping near stream start
  bytes_transferred bigint,         -- real: transferSize / encodedBodySize (0 if cached/opaque)
  buffering_count int NOT NULL DEFAULT 0,
  buffering_ms int NOT NULL DEFAULT 0,
  cdn_cache_status text CHECK (cdn_cache_status IN ('hit','miss','refresh_hit','unknown','na')),
  data_source text NOT NULL CHECK (data_source IN ('real','simulated')))
INDEX (started_at), (track_id), (session_id), (data_source, started_at)

stream_events(                      -- append-only raw log; source of truth
  id bigint PK, event_id uuid UNIQUE NOT NULL,   -- client-generated → idempotent retries
  session_id uuid FK NOT NULL, stream_id uuid FK NOT NULL, track_id bigint FK NOT NULL,
  event_type text NOT NULL CHECK (event_type IN
     ('play','pause','resume','skip','complete','buffering_start','buffering_end','error')),
  occurred_at timestamptz NOT NULL,             -- client clock
  received_at timestamptz NOT NULL DEFAULT now(),-- server clock (detect clock skew)
  playback_position real NOT NULL,              -- seconds
  client_rtt_ms int, load_time_ms int, bytes_transferred bigint,
  data_source text NOT NULL CHECK (data_source IN ('real','simulated')))
INDEX (stream_id), (occurred_at)
```
Why both `stream_events` and `streams`? Events preserve everything and allow re-deriving; `streams` is a cheap upsert at ingest that makes "completion rate by latency bucket" a single `GROUP BY` instead of window-function reconstruction. Outcome rules: `complete` event → completed; `skip` → skipped; stream with no terminal event and session ended → abandoned.

Differences from your sketch: `stream_id` added (a session has many plays of the same track), `event_id` for idempotency, `received_at` for clock skew, `data_source`, `error` event, latency renamed `client_rtt_ms` (honest naming), `artwork_key/audio_key`, `license`.

## AWS / server-side network data (separate tables — different grain & source)

```sql
request_metrics(                    -- app: FastAPI middleware (server-measured)
  id bigint PK, ts timestamptz, method text, route text, status_code int,
  duration_ms real, response_bytes bigint, data_source text NOT NULL)
INDEX (ts), (route, ts)
-- Failed requests = status >= 500 (and 4xx tracked separately)

cdn_requests(                       -- AWS: CloudFront standard log rows
  id bigint PK, ts timestamptz, edge_location text, result_type text,  -- Hit|Miss|RefreshHit|Error
  uri_stem text, status_code int, bytes bigint, time_taken_ms int, time_to_first_byte_ms int,
  data_source text NOT NULL)
INDEX (ts), (result_type, ts)       -- cache hit ratio = Hit+RefreshHit / all

flow_log_records(                   -- AWS: VPC Flow Logs v2 fields
  id bigint PK, window_start timestamptz, window_end timestamptz,
  interface_id text, src_addr inet, dst_addr inet, src_port int, dst_port int,
  protocol int,                     -- IANA number (6 TCP, 17 UDP, 1 ICMP)
  packets bigint, bytes bigint, action text CHECK (action IN ('ACCEPT','REJECT')),
  log_status text, direction text,  -- 'ingress'/'egress' if enabled
  src_role text, dst_role text,     -- derived: 'alb','app','db','nat','internet' (topology)
  data_source text NOT NULL)
INDEX (window_start), (action, window_start), (dst_port, window_start)
```
Why no `session_id` / `latency` on flow logs: VPC Flow Logs don't contain them. Joining flow logs to a listener would be fabrication; correlation between network and engagement is done only via the app-level `client_rtt_ms`/`load_time_ms` on `streams`, and cache status via `X-Cache`.

## Anomalies

```sql
anomalies(
  id bigint PK, detected_at timestamptz, window_start timestamptz, window_end timestamptz,
  kind text CHECK (kind IN ('outbound_traffic','rejected_spike','request_volume','latency')),
  detector text NOT NULL,           -- 'zscore','threshold', later 'isolation_forest'
  metric_value double precision, baseline_mean double precision, baseline_std double precision,
  score double precision, severity text, explanation text NOT NULL,
  data_source text NOT NULL)
```
`explanation` is human-readable ("outbound bytes 4.8σ above 24h rolling mean") — explainability is the point.
